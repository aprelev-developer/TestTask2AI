# Отчёт ревью — `SPEC.md`, запуск 01

> По процедуре [`workflows/spec-review.md`](../workflows/spec-review.md).
> Оба ревьюера в каждом раунде — независимые субагенты с чистым контекстом:
> только текст своей роли/правил проверки и путь к актуальному `SPEC.md`, без
> истории обсуждения продукта.

## Раунд 1

### Замечания ревьюера 1 (внутренняя согласованность)

1. Раздел 8 — формулировка «формирует один итоговый результат» противоречит
   тому же разделу, где при частичном сбое одновременно показываются
   «Обнаружена подмена» и отдельная пометка о незавершённых проверках.
2. Раздел 5 заявляет «три результата», раздел 8 фактически описывает и
   четвёртое сообщение — «Проверка выполнена не полностью» — которое
   пользователь реально видит на экране.
3. Раздел 6, шаг 4 — перечисляет только три исхода, не упоминая техническое
   сообщение о неполной проверке из раздела 8.
4. Раздел 8 — не определено, что показывать, если сценарий 7.5 («Есть
   подозрение») сработал одновременно с технической неудачей проверки по
   одному из сценариев 7.1–7.4 (правило приоритета задано только для
   комбинации «Обнаружена подмена» + незавершённые проверки).
5. Разделы 1/5/7 — один и тот же набор проверок называется то «фрод-сценарии»,
   то «сценарии подмены» без указания, что это одно и то же понятие.
6. Раздел 8 — термин «антифрод-статус» встречается один раз, везде в
   остальном документе используется «результат» — расхождение терминологии.

### Замечания ревьюера 2 (полнота, проверяемость, честность, границы MVP)

7. Раздел 8 — пример технической неудачи проверки («например…») покрывает
   только сценарии 7.1/7.4 и 7.5; для 7.2 (копирование) и 7.3 (наблюдение 5
   секунд) не определено, что считается «не удалось технически выполнить».
8. Требование «утилита не выполняет и не блокирует перевод» (раздел 8/4) не
   имеет соответствующего критерия приёмки в разделе 9, хотя проверяемо.
9. Раздел 9, пункт «Утилита в целом» — объединяет несколько независимых
   условий в одном пункте, что снижает прослеживаемость; в частности,
   «утилита не формулирует итог как гарантию безопасности» не имеет
   конкретного проверяемого критерия (не с чем формально сверить итоговое
   сообщение).

Замечаний по честности категоричных обещаний и по выходу за границы MVP —
не найдено (ревьюер 2 проверял отдельно, нарушений нет).

### Внесённые правки (раунд 1)

- Раздел 1, 5: «сценарии подмены» → «фрод-сценарии» (унификация термина).
- Раздел 5: «Три пользовательских результата проверки» → «Три антифрод-результата
  проверки, а также отдельное техническое сообщение при неполной проверке».
- Раздел 6, шаг 4: добавлено упоминание сообщения о неполной проверке.
- Раздел 8: «формирует один итоговый результат» → «формирует один основной
  результат… может сопровождаться дополнительной технической пометкой»;
  «четвёртый антифрод-статус» → «четвёртый результат проверки».
- Раздел 9: пункт «Утилита в целом» разбит на пять отдельных критериев
  (покрытие за один запуск / неполная проверка / приоритет при частичном сбое
  / отсутствие гарантий — с привязкой к 4 зафиксированным текстам результата /
  перевод не блокируется). Добавлен отдельный критерий по неблокировке
  перевода.

**Что показывать, если при неполной проверке (часть из сценариев 7.1–7.4
технически не завершена) среди завершённых проверок сработал только сценарий
7.5 («Есть подозрение»)?** Варианты:
- показать «Есть подозрение» с пометкой о незавершённых проверках (симметрично
  уже принятому правилу для «Обнаружена подмена»);
- показать только «Проверка выполнена не полностью», не сообщая о сработавшем
  7.5, пока проверка не будет выполнена полностью.

Независимо поднят обоими ревьюерами в трёх из пяти раундов — устойчивый сигнал,
что решение нужно явно зафиксировать, а не оставлять на усмотрение реализации.

## Решение пользователя по открытому вопросу

Пользователь выбрал вариант (а): при неполной проверке, если среди завершённых
сценариев сработал только 7.5 («Есть подозрение»), показывается основной
результат «Есть подозрение» (с указанием найденного неразрешённого скрипта) и
рядом отдельно — техническое сообщение «Проверка выполнена не полностью» (с
указанием, какие проверки не завершены). Найденный сигнал не скрывается
из-за ошибки в других проверках; результат не должен создавать впечатление,
что все сценарии проверены полностью. Правило внесено в разделы 5 (не
менялось по существу), 8 (определение статуса «Есть подозрение», новый блок
правил приоритета «Приоритет при обнаруженной подмене» / «Приоритет при
признаке 7.5») и 9 (два раздельных критерия «Приоритет при частичном сбое
(обнаружена подмена)» и «...(есть подозрение)»), терминология («три
результата», «Проверка выполнена не полностью» — отдельное техническое
сообщение, не четвёртый результат) сохранена.

## Финальный целевой раунд

По просьбе пользователя — один раунд, ревьюеры проверяли только новое правило
и напрямую связанные с ним формулировки (а не весь документ заново).

**Замечания ревьюера 1 (согласованность нового правила):** 5 замечаний — все
редакторские нестыковки, возникшие при первой формулировке правила: (1) общий
абзац о неполной проверке не ссылался на два новых абзаца-исключения; (2)
критерий «Неполная проверка» не оговаривал область действия; (3) неясно, что
именно за «пометка» сопровождает «Обнаружена подмена»/«Есть подозрение» — то
же сообщение «Проверка выполнена не полностью» или другая сущность; (4) новые
абзацы не повторяли правило «если незавершённых проверок несколько — указать
все»; (5) формулировка сопровождающей пометки отличалась текстуально в трёх
местах документа. Пробелов в покрытии всех трёх комбинаций (обнаружена
подмена / есть подозрение / ни то ни другое — каждая с неполной проверкой) не
найдено.

**Замечания ревьюера 2 (честность и проверяемость нового правила):** 1
замечание — фраза «результат не должен создавать впечатление, что все пять
сценариев проверены полностью» не подкреплена конкретным наблюдаемым условием
(оценочная, не поведенческая формулировка); то же самое отмечено и в
зеркальном критерии раздела 9.

**Статусы:** все 6 замечаний — редакторские, без продуктовых решений →
исправлены самостоятельно без дополнительного раунда, по инструкции
пользователя (пункт 6):
- Раздел 8: общий абзац о неполной проверке теперь явно указывает, что
  сообщение либо показывается самостоятельно, либо сопровождает один из двух
  положительных результатов «по правилам приоритета ниже».
- Раздел 8: оба новых блока названы явно («Приоритет при обнаруженной
  подмене» / «Приоритет при признаке 7.5») и оба используют один и тот же
  термин — сообщение «Проверка выполнена не полностью», без синонимов вроде
  «пометка».
- Раздел 8 и 9: везде, где упоминается незавершённая проверка, добавлено «(или
  какие, если их несколько)».
- Раздел 9, критерий «Неполная проверка»: добавлена явная оговорка об области
  действия («и при этом среди завершённых сценариев не обнаружена ни подмена,
  ни признак 7.5»).
- Раздел 9, критерий «Приоритет при частичном сбое (есть подозрение)»: та же
  синхронизация терминологии, что и в разделе 8.
- Оценочная фраза «не должно создавать впечатление…» заменена в обоих местах
  (раздел 8 и 9) на конкретное поведенческое условие: сообщение «Проверка
  выполнена не полностью» обязательно присутствует рядом и не опускается,
  даже если положительный результат уже показан.

**Новых продуктовых противоречий не обнаружено** — все находки укладываются в
рамки пункта 6 инструкции (только редакторские правки, без дополнительного
раунда). Дополнительный раунд после этих правок не запускался — по прямому
указанию пользователя ограничиться самостоятельной проверкой связанных
формулировок.
