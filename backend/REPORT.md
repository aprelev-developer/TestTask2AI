# Отчёт по backend-части — антифрод-утилита ScamTest

> Отчёт покрывает backend-реализацию (Laravel API, защитный модуль
> сравнения, Docker, тесты, workflow ревью) в рамках ДЗ №2. Продуктово-
> аналитическая часть — в `../ScamTest/REPORT.md`, это отдельная роль в
> команде и отдельный документ.

## 1. Цель части работы

Реализовать backend для утилиты, описанной в `../ScamTest/SPEC.md`:
сервис, который принимает наблюдения с тестовой платёжной страницы,
сравнивает их по пяти фрод-сценариям (§7), применяет правила приоритета
(§8) и возвращает один из трёх статусов + техническое сообщение,
журналируя каждое решение. В рамках задачи также требовалось задействовать
параллельных субагентов для базовой оркестрации и собрать повторяемый
workflow.

## 2. Архитектурные решения и почему именно так

- **Laravel + PostgreSQL + Docker** — стек, на котором уже пишет
  разработчик; SPEC.md архитектуру не диктует, перенос смысла не имел.
- **Backend и frontend — два сервиса через API**, не монолит — команда из
  3 человек с раздельными зонами ответственности и раздельными
  контейнерами (аналитик/бэкенд/дизайнер-тестировщик), а не один Laravel-
  проект с общим кодом на всех.
- **Backend делает само сравнение, frontend — тонкий клиент** — не
  диктуется SPEC.md (она archiecture-agnostic), но следует из
  распределения ролей команды («Разработчик: защитный модуль») и держит
  всю бизнес-логику в одной зоне ответственности вместо размазывания между
  сервисами.
- **Domain/Application/Http/Infrastructure с направлением зависимостей**
  (`Domain` не знает про Laravel/Eloquent/Facades) — результат трёх
  раундов внешней архитектурной рецензии до начала кода: dependency
  direction, DTO вместо сырых массивов, Rule/Strategy на сценарий, явные
  контракты `CheckRule`/`CheckResult`/`RuleResult`, транзакция только
  вокруг записи (не вокруг вычисления).
- **Контракт зафиксирован заранее**, до запуска параллельных агентов —
  сигнатуры интерфейсов, схема БД, коды ошибок 404/422. Без этого 4 агента,
  работающих не видя кода друг друга, почти гарантированно разошлись бы в
  именах полей и порядке аргументов.
- **Сознательно не взято в этот цикл**: Serena/семантический индекс кода
  (ценность — на большом/чужом репозитории, кодовая база пишется с нуля),
  `spatie/laravel-data` (простой `readonly`-класс даёт тот же эффект для
  1-2 DTO без зависимости), полный idempotency-key dedup (не требуется ни
  SPEC.md, ни критериями оценки).

## 3. Четыре параллельных агента и их зоны

| Агент | Зона | Обязательный минимум |
|---|---|---|
| A — `domain-builder` | `Domain/Application/Infrastructure/Models`, миграции | Все 5 правил-сценариев, приоритет §8, транзакция вокруг записи |
| B — `api-builder` | `Http/Controllers/Requests/Resources`, `routes/api.php` | Один эндпоинт, валидация, OpenAPI |
| C — `infra-builder` | Dockerfile, docker-compose.yml, Makefile, README «как запустить» | `docker compose up` поднимает всё без ручных шагов |
| D — `spec-test-writer` | `tests/Unit/Domain/Checks`, `tests/Feature/Api` | По тесту на критерий приёмки §9, независимо от реализации A |

Границы — жёсткие, по файлам; никто не трогает чужую директорию.
Общие правила — два skill'а (`spec-compliance`, `backend-conventions`),
а не по одному на агента, чтобы не плодить дублирование одних и тех же
формулировок в нескольких местах.

## 4. Что вернули агенты

- **A** реализовал доменный слой полностью по контракту и, что оказалось
  особенно ценным, **сам сверился** с уже готовым кодом B и D (в режиме
  только чтения) и заранее нашёл 4 интеграционные проблемы до того, как
  я вообще начал сведение (см. п. 5).
- **B** реализовал HTTP-слой и OpenAPI-документацию; вынужденно тронул
  `bootstrap/app.php` (ничья территория) — без регистрации `api:`-группы
  роутов эндпоинт вообще не грузился в чистом Laravel 11 скелете — и явно
  об этом сообщил, а не сделал молча.
- **C** не просто написал файлы, а реально прогнал `docker compose up` с
  нуля, поймал нехватку `memory_limit` для Larastan (128M дефолт крашил
  анализ) и один раз случайно затронул чужие файлы (см. п. 5), тоже
  сообщив об этом явно, а не скрыв.
- **D** написал 37 тестов по контракту и SPEC.md, не читая реализацию A/B
  вплоть до диагностики уже упавших тестов — и, диагностируя, сам поймал и
  корректно разрешил ту же архитектурную нестыковку, что независимо нашёл
  A (см. п. 5), не подгоняя тест под код, а исправив неверное
  предположение о типе.

## 5. Интеграционные проблемы, найденные при сведении

Найдено и исправлено на этапе интеграции (до старта формального
`backend-review`):

1. Отсутствовали DI-биндинги интерфейсов репозиториев
   (`AppServiceProvider`) — ничья территория, эндпоинт не поднимался.
2. `CheckResultResource` заворачивал ответ в `{"data": {...}}` по
   умолчанию Laravel — нарушало контракт плоского JSON.
3. Внутри Docker-образа физически нет `.env` (осознанно, без секретов в
   образе) — что-то в бутстрапе Laravel падало на прямом
   `file_get_contents`; добавлена секрет-свободная копия `.env.example`
   как база.
4. Фикстуры Агента D изначально предполагали Eloquent-модель вторым
   аргументом `CheckRule::evaluate()`, а не Domain DTO — расхождение,
   которое независимо поймали и правильно разрешили и A (через
   перекрёстную проверку), и D (через диагностику упавшего теста),
   сойдясь на архитектурно верном варианте без моего вмешательства.
5. Один коммит по невнимательности подхватил уже застейдженные файлы
   аналитика (`git commit` берёт весь индекс, а не то, что добавил
   последний `git add`) — отловлено до пуша, отменено `git reset --soft`
   без потери данных, перекоммичено точечно.
6. Кэш PHPStan (146 955 строк, служебные файлы) по невнимательности попал
   в первый коммит скелета — не сверил `.gitignore` заранее; убрано
   отдельным коммитом.

## 6. Workflow `backend-review` и его результаты

Собран по образцу `spec-review.md` аналитика, адаптирован под код: вместо
двух ревьюеров спецификации — `contract` (стыковка A↔B, идёт первым) →
параллельно `correctness` (SPEC.md) + `quality` (backend-conventions) →
`backend-breaker` (чёрный ящик, отдельная сессия). Полное описание —
`workflows/backend-review.md`, полный протокол первого прогона —
`reviews/backend-review-01.md`.

Раунд 1 нашёл 3 находки, все приняты и исправлены: отсутствие
`incomplete_message` (SPEC.md §8) в контракте ответа; статус «Подмена не
обнаружена», ложно показывавшийся при неполной проверке (прямое нарушение
§8 — нашёл `backend-breaker`, причём это была ровно та ситуация, которую
Агент D заранее описал в комментарии к своему тесту как риск, но которую я
сам, интегрируя код, не учёл в `CheckResultResource`); молчаливая обрезка
пробелов в наблюдаемых значениях Laravel'овским `TrimStrings` (нарушение
инварианта «raw observations»). Формальный второй раунд (шаг 5 workflow) не
проводился — заменён прогоном полного набора тестов и живыми `curl`-
запросами; в самом workflow-документе это отмечено как допустимое только
для точечных правок, не общее правило.

## 7. Что сработало хорошо

- Зафиксированный заранее контракт (сигнатуры, схема БД, коды ошибок)
  реально предотвратил рассинхрон между 4 параллельными агентами — все
  трое (A, B, D), работая не видя кода друг друга, независимо сошлись на
  одинаковой интерпретации там, где контракт был неполон (например, что
  `run_id` передаётся в `RunCheck` отдельно, а не полем `CheckInput`).
- Независимость Агента D (тесты по SPEC.md, не по реализации) — не
  формальность: именно так поймана и корректно разрешена архитектурная
  нестыковка Eloquent/Domain DTO.
- `backend-breaker` поймал 2 реальных нарушения задокументированных
  инвариантов, которые прошли мимо остальных трёх этапов ревью (включая
  меня самого при проектировании исходного API-контракта) — оба
  воспроизводились на самых обычных запросах, не экзотических граничных
  случаях.
- Явная граница по файлам между агентами (никто не трогает чужую
  директорию) сработала — единственные два случая выхода за территорию (B
  правит `bootstrap/app.php`, C случайно переформатировал файлы D через
  `make pint`) были явно и честно задекларированы самими агентами, а не
  скрыты.

## 8. Что не сработало или оказалось избыточным

- Я сам дважды ошибся при интеграции ещё до старта формального ревью:
  расширил разовую просьбу «не пушить один skill» до «не пушить весь
  `.claude/`» без необходимости (пришлось откатывать по вопросу
  пользователя), и спроектировал API-контракт в `backend-conventions` без
  поля для технического сообщения §8, хотя сам же сформулировал это
  правило в `spec-compliance` — нашлось только на ревью, не раньше.
- Первый коммит скелета задел чужой застейдженный индекс и кэш PHPStan —
  оба случая — цена недостаточной проверки `git status`/`.gitignore`
  перед первым коммитом каждого нового шага, не системная проблема
  подхода.
- Формальный второй раунд `backend-review` (шаг 5) в реальности заменён
  более лёгкой проверкой (тесты + curl) — работает для мелких находок этого
  раунда, но это осознанное отступление от процедуры, а не то, что
  workflow предполагает по умолчанию.
