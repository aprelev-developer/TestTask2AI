# Backend git workflow

Постоянное полномочие от пользователя: коммитить и пушить бэкенд-работу без
отдельного разрешения на каждый раз, в рамках правил ниже. Действует только
на `feature-aprelev` и ветках, порождённых от неё, — моей территории.
`develop`/`main` эта скилл не касается и никогда не форс-пушит.

## Когда коммитить и пушить

После каждого полезного законченного действия или конечного результата —
коммит + пуш сразу, не копить изменения в один большой коммит в конце
сессии.

## Что стейджить

`git add` только то, что в моей зоне: `backend/` и явно затронутые корневые
файлы (например `.gitignore`), если именно я их менял по просьбе
пользователя. Никогда не подхватывать чужие уже застейдженные или
незакоммиченные изменения (например `ScamTest/*`) — они не моя территория,
даже если попадаются в `git status`.

## Ветки

Если несколько агентов работают по-настоящему параллельно и независимо —
разумно развести их по отдельным веткам, порождённым от `feature-aprelev`
(это и есть подход, который сама домашка рекомендует для параллельной
работы). Не плодить ветки бесцельно: новая ветка — только под реально
независимый параллельный поток, не под каждую мелкую правку.

## Формат коммита

- Сообщение — на русском, название ветки — на английском.
- Сообщение описывает, что **сделано** (свершившийся факт), а не что
  планировалось или будет сделано.
- Кратко — без раздутых описаний и списков на полстраницы.

## Что НЕ делать

- Не открывать pull request самостоятельно. Когда он понадобится — сказать
  об этом пользователю, PR делает он сам.
- Не указывать соавторство (`Co-Authored-By` и подобное) — автор коммита
  только тот, что уже закреплён в `.git` config, без добавлений.
- Не писать `git push origin <branch>` и не задавать автора вручную — просто
  `git push`. Лишние ручные уточнения — источник трудноисправимых ошибок.
- **Единственное техническое исключение**: у только что созданной ветки нет
  upstream, и обычный `git push` в этом случае технически откажет с ошибкой
  (это поведение git, а не самодеятельность) — на самом первом пуше новой
  ветки нужно один раз задать upstream (`git push -u origin <branch>`),
  дальше на этой же ветке — снова просто `git push`.
